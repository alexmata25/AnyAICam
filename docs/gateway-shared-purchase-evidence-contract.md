# Gateway shared purchase evidence: proposed v1 handoff

**Status: proposed and disabled.** The existing generic VMS licence and hardware order do not establish an edition-specific purchase bound to an installation. AAC Plus's separately maintained implementation has not been inspected or changed. No current producer, trusted key distribution, transactional revision store or purchase-evidence confirmation path exists. The Gateway prototype is unmounted, `PURCHASE_EVIDENCE_CONTRACT_READY=False`, and `gateway_edition_evidence` continues to report verified purchase evidence unavailable. This document is an integration proposal, not an instruction to enable billing or ship a new security protocol.

## Record v1

All fields below are required, including explicit `null` where allowed. IDs are server-owned opaque ASCII references matching `[A-Za-z0-9_.:-]{1,128}`. Do not put payment credentials, device secrets, personal contact data, signed licence contents or Claim ID in this record. A record's issuer must derive facts from authoritative server-side systems, not the browser or a device's self-reported edition.

| Field | Meaning and validation |
| --- | --- |
| `schema_version`, `evidence_id`, `revision` | Integer `1`, stable unique purchase-evidence ID, and strictly positive monotonic integer revision. Booleans are not integers. |
| `customer_id`, `edition` | Authenticated account ID resolved by the shared server; `local_gateway` or `cloud_gateway` from the server's approved product classification. |
| `stripe_product_id`, `stripe_price_id` | Actual canonical `prod_` and `price_` identifiers classified and verified by the server. Prefix checks are formatting only; they do not prove classification or price. |
| `payment_reference`, `payment_status`, `reversal_state` | Canonical payment/invoice reference and current authoritative status. Status values: `paid`, `pending`, `unpaid`, `canceled`, `refunded`, `revoked`; reversal: `none`, `partial_refund`, `refunded`, `disputed`, `unknown`. Only `paid` with `none` is a candidate. A partial refund currently fails closed pending an agreed allocation policy. |
| `license_reference`, `license_customer_id`, `license_status`, `license_capacity` | Reference to the separately purchased or included VMS licence; its current owner, status (`active`, `pending`, `revoked`, `expired`) and positive signed licensed capacity. This record does not replace or extend the signed licence. |
| `fulfillment_kind`, `hardware_order_id`, `hardware_unit_id`, `fulfillment_status` | `software_only` uses null hardware IDs and `not_applicable`; `preinstalled_appliance` requires a server-owned order and individual unit ID, with state `paid`, `preparing`, `configuring`, `testing`, `ready_to_ship`, `shipped`, `delivered` or `cancelled`. Before shipment it waits for fulfillment. |
| `installation_id` | Null until securely associated through the existing authenticated ownership and rotating possession-challenge flow. The stable Claim ID is not an authorization token and is not used as this proof. |
| `cloud_subscription_id`, `cloud_subscription_status`, `cloud_quantity` | Null for Local. Cloud requires a canonical Cloud Gateway subscription, status (`active`, `pending`, `past_due`, `canceled`, `unpaid`, `revoked`) and positive integer purchased camera quantity. Only active status is a candidate. Quantity is a subscription capacity, not proof that any individual camera is assigned or licensed. |
| `issued_at`, `expires_at` | Integer Unix UTC seconds; require `0 <= issued_at <= current time < expires_at`. The shared team must agree an operational freshness and refresh policy; this format does not create a grace period. |

## Producer and consumer

1. The shared checkout/Customer Portal team owns the canonical customer, verified provider object and payment/reversal ledger, product/Price classification, VMS licence and hardware fulfillment facts. It must resolve a purchase-before-registration flow by an independently authenticated account-binding procedure, then publish a durable current snapshot and audit trail. Event order, unique event IDs and monotonic revisions must prevent an old paid event from overwriting a later refund or revocation. The website can choose products but cannot assert payment or account ownership.
2. Gateway consumes only a server-authenticated evidence snapshot from the approved producer. The synthetic interoperability proposal uses HMAC-SHA-256, lowercase hexadecimal tag, a secret of at least 32 bytes, and ASCII bytes of JSON serialized with lexicographically sorted keys, `,`/`:` separators, `ensure_ascii=True`, and no NaN. Keys and expected issuer identity must come from a server-controlled secret mechanism, never the request body. This is a symmetric MAC, not a non-repudiable digital signature. Key identifiers, rotation, transport authentication, canonicalization across implementations, secret access and independent security review must be agreed before use; do not deploy the prototype as a production verification scheme.
3. The current canonical payment/reversal ledger, current licence, current provider product mapping and current customer/appliance/claim ownership take precedence over a prior signed snapshot. Unreadable, missing, ambiguous, expired, revoked or stale evidence fails closed; an outage cannot be rewritten as a permanent cancellation. Before any confirmation or entitlement write, the consumer must transactionally lock and revalidate those sources and the completed, current possession-verified claim. A signature alone establishes none of those facts.
4. A durable, locked consumer revision record must bind `evidence_id` to its most recent revision, exact document digest, immutable customer, edition, Product, Price, Cloud subscription, licence and hardware-unit binding digest, installation association and audit events. Same revision and same digest is an idempotent replay; same revision with different content and lower revisions are rejected. A higher revision may update eligible status or quantity, but it cannot silently change those bound identities; after an installation is bound it cannot silently change installation. A legitimate Price or subscription replacement, transfer or hardware replacement requires a separate authorized workflow and new evidence. Persist revocations and revision changes atomically with reconciliation, so stale signed records cannot restore service. The current prototype only evaluates a supplied previous snapshot in memory and does not provide this durable store or concurrency guarantee. The binding digest format changed in this source-only revision and must not be treated as compatible with any earlier synthetic snapshot.
5. Cloud quantity reductions must be serialized against assignments and fail closed for any over-allocation until the existing assignment/retirement service resolves it. Refunds, cancellations, disputes, ownership changes and unavailable verification must never grant or restore access. Local recording, purchased software licences and signed local camera capacity remain independent of recurring remote-access status.

Software-only orders can wait for the customer to install and complete the existing authenticated claim; preinstalled orders wait for verified fulfillment and then the same claim. Neither a shipped unit nor a purchase authorizes possession or a transfer. The prototype returns `awaiting_fulfillment`, `awaiting_claim`, `ineligible` or `candidate_only`; even `candidate_only` is not a verified entitlement, confirmed edition or permission to activate. It returns `unavailable` under its unchanged default-off gate.

## Required implementation and acceptance

The shared team must deliver the authoritative edition-specific producer, trusted account attachment, validated Stripe Product/Price mapping, canonical current payment and reversal linkage, licence and hardware-unit associations, Cloud subscription/quantity source, authenticated transport and key-management proposal, and lifecycle/audit semantics. Gateway must implement durable revision locking, independently obtain current customer/claim/installation ownership, revalidate all sources transactionally, integrate existing edition evidence and camera assignment services, and verify PostgreSQL concurrency and signed HTTP behavior in a separately approved isolated environment. The held AWS adapter, default-off Checkout, paid activation and stable Claim ID stops are unaffected. No real Price or secret is supplied by this contract.
