# Local Gateway appliance edition identity

`appliances.gateway_edition` is nullable and has no backfill. A missing or NULL value retains legacy capacity behavior; Local Gateway checkout and remote access fail closed without an explicit matching Local Gateway identity. Existing per-camera subscription and customer data are unchanged.

The existing customer onboarding route accepts `gateway_edition: local_gateway` only when the actor has a current global administrator grant. The value is bound to each newly created appliance and its new customer within the onboarding transaction. Appliance-provided data never assigns the field. Other onboarding paths continue to create legacy NULL records.

The Claim ID flow creates a claimed appliance without an edition; the device's reported edition is not proof of server billing identity. The global administrator's Partner portal, Cloud Adapters tab, lists claimed appliances awaiting verification, along with customer, credential and heartbeat information. No trusted edition purchase evidence is currently linked to this claim flow. Consequently, confirmation is unavailable: `POST /api/operations/appliances/{appliance_id}/confirm-local-gateway` rejects an unassigned edition with 409 even for a global administrator. It still reports an already-confirmed Local Gateway idempotently and refuses other editions or a mismatched customer. It makes no assignment or audit write while blocked. A claimed computer does not appear on My subscription until it has a trusted edition.

To enable customer-facing confirmation, first establish a reliable purchase or provisioning record and implement explicit administrator review of the evidence and customer/appliance pairing, with transaction-scoped revalidation and audit. A typed reference, customer selection, claim, heartbeat, or device-reported edition alone is not proof of purchase. No customer-facing review action is enabled.

The unexecuted `20261104_appliance_edition_provisioning_decisions` migration proposes a durable customer, appliance and claim binding for either Gateway edition, with a source, reference, evidence version, verifying administrator and verification time. It permits at most one unrevoked decision per appliance and does not grant a license or backfill a decision. This schema is not evidence by itself. The internal-test service described below is not exposed through HTTP. An administrator's arbitrary typed reference must not be stored or displayed as independently verified evidence. Do not run this migration as part of this work.

`gateway_edition_evidence.verify_edition_evidence` defines `verified_gateway_purchase` and `authorized_internal_provisioning`. Purchase verification remains unavailable: it needs a server-verified paid edition-specific order and appliance association. Internal test provisioning now has an **unrouted** service in `gateway_internal_provisioning.py`. A live global administrator can authorize a claimed customer-owned appliance for internal testing using the fixed server-defined basis `internal_test_claimed_appliance`. The transaction records the authorization and its audit entry; the verifier checks the record, version, status, matching audit, current claim and ownership. It is an administrative test decision, not independent proof of a purchase, a license grant or evidence of customer purchase eligibility. Arbitrary operator references and self-reported device values are not its basis.

The same module prepares transaction-wrapped confirmation and an edition decision with an audit entry, but has no registered route or UI. The existing HTTP endpoint remains blocked. `20261105_internal_gateway_provisioning_authorizations` is additive migration source only and has not been executed. Before exposure, verify PostgreSQL locking and claim concurrency, deployment/test-only controls, schema availability, CSRF and HTTP authorization, audit/revocation policy, and end-to-end behavior. The prepared code does not alter customer entitlements or contact Stripe.

Internal test services require both an explicit `ANYAICAM_ENV` of `development` or `test` consistent with loaded settings and `ANYAICAM_INTERNAL_GATEWAY_PROVISIONING_ENABLED=true`; the default is disabled. Prepared authorization, revocation, version-update and confirmation handlers in `gateway_internal_test_routes.py` are deliberately unmounted. They require the existing signed double-submit CSRF token and live global administrator checks. Version changes and revocations are transactionally audited, and verification requires intact version history. A global administrator may revoke by the recorded authorization identity and version even after claim invalidation or an ownership change; that exception cannot authorize or advance a version.

The unexecuted `20261106_one_current_completed_claim_per_appliance` source migration adds a partial unique index for non-revoked completed claims with an appliance ID. The unexecuted `20261107_one_current_claim_session_per_device` migration adds a case-normalized partial unique index for non-revoked pending or claimed device sessions. Claim-begin requires that index, expires stale sessions, and uses conditional retry/confirmation/completion updates. Existing duplicate current rows would make index creation fail and require independent review; no rows are changed by this source work. SQLite synthetic races passed; actual PostgreSQL locking and the full claim lifecycle remain unverified.

Local Gateway remote-service eligibility now requires an edition decision backed by its current authorization and customer/claim. Missing, invalid or revoked evidence denies future eligibility while retaining the edition and historical decision; a new authorization requires explicit confirmation. This includes existing Local Gateway editions assigned by the earlier onboarding path without a decision. Full VMS retains its established separate remote path. Missing or unreadable Gateway schema fails the Gateway check closed; absent schema cannot prove that an otherwise unidentified device is legacy. No local license or recording behavior is changed. A disconnected device with an existing signed offline lease remains governed by its existing expiry.

`gateway_schema_readiness.inspect_gateway_schema(db, backend)` provides read-only checks against a caller-supplied connection for required column names/types, index structure, migration markers and dependencies, and duplicate current claims. It neither connects nor runs migrations. Claim-begin separately requires the live-session index and returns 503 if it cannot verify it; thus schema rollout is a prerequisite for new or resumed claims. Do not expose these changes or run migrations until duplicates, migration ordering, actual PostgreSQL metadata/locking, compatibility and isolated HTTP acceptance have been independently checked.

The queue shows the completed `appliance_claims` record and the customer's `customer_entitlements` VMS license record as contextual records, explicitly not edition evidence. It flags duplicate current claims and customer mismatches. `build_orders.sync_from_stripe_event` can grant that software license from a verified paid checkout, but its VMS price/capacity identifies software capacity rather than a Gateway edition or appliance. `hardware_orders` likewise records a customer and hardware SKU, not a claimed appliance's Gateway edition. The global-administrator onboarding assignment applies to newly created appliance rows; copying it to a separate claimed device would be an unverified transfer. Until an authoritative edition-specific purchase or provisioning source and binding exist, no evidence can safely be backfilled or confirmed.

Claim completion does not itself make a computer ready: the existing `appliance_readiness.appliance_activated` check requires a live credential and, for a claimed appliance, evidence of its authenticated heartbeat. Checkout eligibility, customer status and remote-access issuance reuse that check; a revoked, retired or released appliance fails closed. The separately purchased local license and signed capacity remain independent of remote subscription state. A previously issued offline lease remains governed by its signed expiry, which cannot exceed 24 hours; a disconnected device cannot learn of a later revocation immediately.

The schema source is the additive `20261103_appliance_gateway_edition` entry in `app/db_migrations.py`; do not execute it without separate authorization. Before rollback, stop application reads and writes of this field, then consider schema removal separately. Never automatically remove the column or its data. Local Gateway checkout remains disabled.

Before acceptance, verify global-admin grant enforcement and customer isolation through HTTP, safe behavior with missing schema and NULL records, purchased-license capacity before subscription and after cancellation, concurrent billing updates, and snapshot rollback/online revalidation.
