## Smallest proposed extension, subject to source and owner approval

1. In the existing server-owned product catalogue and Checkout construction, classify `local_gateway_remote` and `cloud_gateway` separately from generic VMS plans; bind the server-selected Product/Price, authenticated customer and checkout intent. Do not hardcode or invent live Price IDs. The owner's candidates `price_1UY8t6GllhK80H2nSu6nv5XD` and `price_1UY8vgGllhK80H2nDydHxToQ` remain unverified for mode, active Product classification, USD 999 and monthly interval.
2. Reuse the existing verified dispatcher and canonical fetch/reversal checks. Feed a durable, versioned edition-specific purchase record from the existing checkout/entitlement transaction, not a new parallel payment system. Preserve event ID idempotency, canonical object identities, existing lock ordering, audit and full VMS/refund/upgrade paths. Unmatched or ambiguous events remain quarantined; no unrelated tenant is fenced by guessing.
3. Associate the existing licence and purchase with a customer-owned installation only after the existing possession-verified claim, with a separate unit association for each preinstalled appliance. Software-only remains pending until installation; hardware remains pending through fulfillment. Keep one-time VMS licence and signed local camera capacity independent of the recurring Gateway subscription.
4. Add only the missing durable data: an authoritative versioned edition-specific purchase/fulfillment-to-unit and installation evidence record (or equivalent reviewed extension of existing order/provisioning records), with unique identifiers, source revision/digest, status/revocation and audit. Hardware quantity alone is not a unit identity. The Gateway checkout already contains **unexecuted preparation** for `appliances.gateway_edition`, `appliance_edition_provisioning_decisions`, Cloud subscription evidence/camera bindings, checkout attempts and claim-ID tables. These are proposals, not a deployed schema or a completed authoritative purchase ledger; compare against the actual target migration history before designing an additive change. No unknown editions or historical purchases may be backfilled.
5. Wire `gateway_edition_evidence.verify_edition_evidence` to the actual authoritative purchase verifier only after current customer, paid/unreversed state, product, licence, hardware unit and completed claim can be revalidated together in a transaction. The v1 synthetic contract and `gateway_purchase_handoff.validate_signed_candidate` are default-off prototypes, not a mandatory separate service or a production HMAC protocol; use direct trusted database access if the authoritative components share a transaction, or separately review authenticated transport if they do not.
6. For Cloud Gateway, derive a paid camera quantity only from the verified Cloud-specific subscription, then use the prepared `cloud_gateway_subscription_evidence` and `cloud_gateway_camera_entitlements.produce_paid_binding`/retirement flows after review. Lock and reconcile quantity reduction, cancellation, reversal, mapping changes and ownership transfer; generic camera slots are not Cloud purchase evidence. For Local, retain the existing per-appliance subscription and signed lease, with authorization-bound Checkout and late-payment reconciliation still stopped pending acceptance.
