# Local Gateway isolated HTTP acceptance and continuity boundary

## Isolated acceptance preparation

Run only after separate approval for resources, dependencies, and any disposable migration execution. Use a loopback-only test application, disposable database, synthetic accounts/appliances/signing keys and a local mocked Stripe adapter. Deny outbound network, live credentials, and production data. Keep the real checkout feature switch disabled outside this isolated harness; never enable it in a deployed service. The fixture must explicitly inject the test configuration and replace provider calls before app startup. It must not let application initialization reach a real database or provider. Do not start or stop a VM.

Prepare HTTP fixtures and assertions for:

1. **Onboarding authority:** a live synthetic global-admin grant may create a Local Gateway; a partner-scoped admin, customer, appliance credential, expired grant and unauthenticated caller cannot set the edition. Confirm the row belongs to the intended customer and that existing NULL rows remain NULL. Confirm client-supplied edition fields cannot change an existing record.
2. **Tenant isolation:** create two customer/appliance pairs. Customer A cannot check out or retrieve an entitlement for B; exercise owned, foreign, missing, NULL-edition and Cloud-edition appliance records.
3. **Checkout authentication:** reject missing, viewer, foreign-customer, revoked-appliance and unlicensed requests. For a permitted Local Gateway, assert a mocked checkout uses one unit of the configured 999-cent monthly price, its own appliance key, and no real Stripe call.
4. **Webhook verification and retries:** signed synthetic event reaches dispatch; invalid and missing signatures never mutate billing. Test duplicate same event and a failed write followed by retry/restart; verify step bookkeeping and state in the disposable database.
5. **Lifecycle:** simulate current-provider states for cancellation, expired subscription, failed invoice, recovery, dispute, refund and replacement. Deliver duplicate, old and concurrent events; require stale subscription IDs never change the replacement and current provider payment evidence before issuing a lease. Verify no local recording/playback or purchased capacity changes.
6. **Capacity:** before any remote subscription, a server-identified Local Gateway with a signed purchased license provisions up to its purchased capacity independently of camera plans. Repeat after cancellation and compare NULL-edition/per-camera VMS controls.
7. **Remote lease:** use generated Ed25519 test keys and the actual test trust registry. Verify correct tenant/appliance/nonce, 24-hour maximum, expiry without network, revoked keys, cancellation, restart, persistence failure and simulated clock rollback. Do not treat a simulated process restart as a full-machine snapshot test.

These are acceptance specifications, not executed HTTP tests. `app/tests/local_gateway_http_harness.py` provides an in-process ASGI client, synthetic identities and signing key, a provider fake, a disposable SQLite file, and socket and SQLite guards. A full VMS fixture and HTTP cases have been prepared but have not been executed or independently validated. Existing lightweight unit tests do not establish HTTP or concurrency behavior.

### Mandatory isolation before acceptance

Python-level SQLite guards are defense in depth, not filesystem confinement. A captured `sqlite3.Connection.set_authorizer` base-class descriptor can remove the connection authorizer and permit `ATTACH`, as the synthetic regression demonstrates. Native code and pre-existing handles can also fall outside those Python guards. HTTP acceptance therefore requires independently verified **OS-enforced filesystem isolation** for the effective test process: it must permit the disposable database and required test resources while preventing access to production databases and other sensitive data, and prevent writes outside approved disposable locations. The verification must account for inherited handles, alternate paths and links, and must use controlled positive and negative probes against synthetic resources. Required application and interpreter files may need read access; merely setting a temporary directory or environment variable is not sufficient.

Independent OS-enforced outbound network denial is also required; socket monkeypatches, an AppContainer label or an operator assertion alone do not establish it. The preflight runner has separate unconditional failure gates for filesystem and network isolation because neither verifier is implemented. Do not run migrations or HTTP acceptance until both verifiers are implemented and independently pass, other prerequisite and side-effect reviews are complete, and the owner separately authorizes those actions. This requirement does not itself modify accounts, firewall rules, or infrastructure.

## Full-machine snapshot boundary (design only)

A snapshot can rewind a cached lease, process memory, wall clock, monotonic clock and local trust state together. None of those local values proves continuity after a complete restore. Existing restart denial and clock checks therefore do not detect every snapshot rollback.

The smallest candidate boundary is an independently maintained, authenticated online authorization check at the remote-access entry point, outside the restorable appliance snapshot. It must bind customer, appliance, current subscription and an unpredictable fresh challenge, and deny or require a fresh response whenever continuity cannot be established. It must not depend on a counter or key stored only inside that snapshot. How an actual restore is detected, where that independent authority runs, its failure behavior, and compatibility with the approved offline lease remain unresolved security and owner decisions. No new grace period or snapshot policy is approved or implemented by this document. Local viewing, recording, playback and purchased capacity must remain independent of remote authorization.
