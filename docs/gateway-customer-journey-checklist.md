### Purchase-to-installation handoff

`gateway_purchase_handoff.reconcile` is an **unmounted, read-only Gateway-side preview**, not an authoritative purchase producer or activation endpoint. With an authenticated customer-owner supplied by a future trusted caller, it reads that customer's existing VMS-licence Checkout reference for software-only orders or hardware order ID for a single preinstalled appliance, and optionally verifies that an appliance is currently owned by that customer. It reports awaiting fulfillment, awaiting installation claim, pending verification, an edition conflict, or an ineligible observed payment/licence state. Duplicate, missing or cross-customer rows are denied. Replays are repeatable and write nothing. It never verifies a paid Gateway edition, associates the order with the appliance, interprets a Claim ID as possession, grants a licence or activates service. A nominally active software-licence row is displayed only as an observed prerequisite; expiry and reversal verification remain necessary. Cloud paid camera quantity is not asserted from generic account-wide plan quantities.

The single intended authoritative contract, to be supplied by the shared purchase/provisioning system, must provide a durable, uniquely identified and versioned server-owned record with: authenticated customer ID; order and canonical verified payment/entitlement references and current reversal status; explicit Local or Cloud Gateway product classification; separately purchased or included VMS-licence reference and signed camera capacity; software-only versus preinstalled fulfillment and, for hardware, order unit and current fulfillment state; intended installation association established by the existing secure provisioning/claim flow; and, for Cloud, the verified edition-specific subscription ID and purchased camera quantity. It must retain audit history, enforce idempotent event/order identifiers, reject conflicting duplicates and stale replays, and support cancellation, refunds and ownership changes without silently reactivating. Association to an installation must be revalidated transactionally with the current customer and completed possession-verified claim; software-only orders legitimately wait for an installation and unshipped hardware waits for fulfillment. A claimed ID or customer-selected edition is never purchase evidence.

AAC Plus / website integration must supply the trusted server-owned edition-specific purchase and fulfillment record, canonical customer and provider object correlations, applicable licence provenance and a safe installation-provisioning association; the website may submit a selection but cannot assert paid status. The existing Gateway verified-purchase evidence source remains unavailable until such an authenticated producer and verifier exist. `build_orders.py` and `hardware_orders.py` already record generic verified purchase/fulfillment state; `customer_downloads.py` restricts downloads to a licensed owner. None of those generic records alone binds a Gateway edition to a claimed installation. The checkout/stable-claim/paid-activation stops remain unchanged. This checkout's storefront material was reviewed read-only; the separately maintained AAC Plus project and its live contract were not available for direct review.

The checked-in `storefront/staging/checkout-session.php` describes a purchase-before-registration flow with later customer attachment; its companion handoff test is explicitly a staging/review copy, not evidence of current production behavior. The shared team must define and verify that attachment before associating a Gateway purchase with an authenticated account. A browser-supplied Stripe customer ID, email or edition is a lookup/selection only; it is not authority to attach a payment or claim an appliance.

The proposed v1 fields, producer/consumer responsibilities, authentication, revisions, revocation and software/hardware claim states are specified in `gateway-shared-purchase-evidence-contract.md`. A default-off synthetic signed-evidence validator checks the proposed format and returns candidate-only; it is not connected to purchase verification, a durable revision store or edition confirmation. The shared team must supply the authoritative producer and agree the security and lifecycle contract before integration.
